## 1. Project Overview

**Inland Property** is a web application for property management, property
catalog, CRM (lead management, follow-up, contacts, activities), AI assistant,
notification, and internal administration.

**Target users:**
- **Public visitors (tamu):** browse property catalog, KPR calculator, submit
  lead inquiries
- **Registered clients (viewer):** same as guest + login, save preferences
- **Agents:** manage leads, follow-ups, properties, create invoices
- **Marketing:** read-only CRM access, create leads
- **Admin:** manage users, approve agents, view reports, system logs
- **Super Admin:** full access including user deletion, audit trail, AI summary

**Current status:** The application is **functional** with 36 page routes, 32
API endpoints, and 17 database migrations. A PHASE 0 security audit
(2026-08-08) identified CRM security gaps. PHASE 1A (emergency security) and
PHASE 1B (ownership RLS) are **CLOSED** in migrations. PHASE 0.75 (database
baseline) and PHASE 2+ are **pending**.

**Key architectural patterns:**
- **Browser services → PostgREST:** All 8 service files use the browser
  Supabase client (`createBrowserClient` with anon key). CRM data operations
  go directly browser → PostgREST. There are **no CRM server actions**.
- **API routes for server-only operations:** Operations requiring
  `SUPABASE_SERVICE_ROLE_KEY` (notifications, audit logging, AI quota,
  WhatsApp) delegate to API routes.
- **proxy.ts is layer 1 (optimistic):** Route protection is an optimistic
  check. Real enforcement is at the API route level (`lib/api-auth.ts`) and
  database level (RLS).

## 5. Authentication

### Provider
**Supabase Auth** — email/password + Google OAuth.

### Login flow
1. User submits email + password at `/login` (`app/login/page.tsx`)
2. `supabase.auth.signInWithPassword()` called client-side
3. On success, `useUser()` hook detects auth state change and fetches user
   profile from `public.users` table
4. Row-level auto-insert: if no `users` row exists, `usePermissions()` creates
   one with `role: "viewer"` (on first login)
5. Google OAuth: redirects to Supabase → callback at `/auth/callback`

### Registration flow
- **Member:** `/register` → creates auth user + inserts `users` row with
  `role: "viewer"`
- **Agent:** `/register/agent` → creates auth user + inserts `users` row with
  `role: "agent"`, `status: "pending"`, `is_approved: false`. Admin must
  approve at `/admin/users`.

### Session handling
- Uses Supabase `@supabase/ssr` with cookie-based sessions
- `proxy.ts` calls `supabase.auth.getUser()` (verifies token against Supabase
  Auth server) — NOT `getSession()` (forgeable)

### Route protection
- `proxy.ts` is the first layer (optimistic). Three checks:
  1. Unauthenticated user on protected page → redirect to `/login`
  2. Authenticated user on auth page → redirect to `/dashboard`
  3. Authenticated user on protected page → check role via `canAccessRoute()`
- `lib/api-auth.ts` is the second layer (authoritative):
  - `requireAuth()` — authenticated + not blocked (pending/suspended)
  - `requireRole(allowed)` — role-based guard
  - `requirePermission(permission)` — permission-based guard

### Public routes (no login required)
- `/dashboard`, `/properties`, `/kpr-calculator` — public showcase
- `/login`, `/register`, `/register/agent`, `/forgot-password`
- `/legal/*` — legal pages
- `/api/leads` (POST) — public lead intake with rate limiting
- `/api/chat` (POST) — public AI chat with rate limiting

### Protected routes
- `/crm`, `/admin`, `/reports`, `/invoices`, `/projects`, `/surveys`,
  `/notifications`, `/settings`

`docs/crm/02-roles-permissions.md` §0.

**CONFLICT: `superadmin` (lowercase) exists in database but is being removed
from `is_staff()` by migration 016.** `normalizeRole()` handles it at runtime.
All existing users have `'super_admin'` (with underscore).

## 7. Property Management

### Property listing
- **Statuses:** `draft`, `review`, `published`, `sold`, `rented`, `archived`
- **Listing types:** `jual` (sale), `sewa` (rent)
- **Property types:** 10 types (rumah, apartemen, ruko, tanah, etc.)
- Public catalog at `/properties` with search, filter, grid/table views
- Detail page at `/properties/[id]` with gallery, specs, agent info, inquiry
  form, and structured data (JSON-LD `RealEstateListing`)

### Property ownership
- `created_by` records who created the listing
- `assigned_to` records the responsible agent
- `PropertyOwner` stores owner information (separate from `users`)

### Property assignment
- `PATCH /api/properties/[id]/assign` — assigns agent (server-side, triggers
  notification)
- Publishing rule: `requiresAgent(status)` — a listing can only be published
  if it has an assigned agent; otherwise downgrades to `draft`

### Property media
- Upload via `POST /api/media/upload` (authenticated, ownership-checked)
- Supabase Storage bucket `property-media`: 10MB max, JPEG/PNG/WebP only
- Server-side watermark via `sharp` (`lib/watermark.ts`) — composite
  `public/watermark.png` at center, 70% opacity, 30% size
- MIME type check is **client-declared** (no magic byte verification)

### Relationship with CRM
- Properties can be linked to leads via `crm_interests` (lead-property
  relationship)
- `getPropertiesForLead()` in `crm.service.ts` queries available properties
- Lead capture modal on property pages (`LeadCaptureModal`)

## 8. CRM Architecture

### Lead

**Source:** Public intake form (`POST /api/leads`) or manual creation by
agents/admins at `/crm/leads/create`.

**Creation flow (public intake):**
1. `POST /api/leads` — public endpoint, rate-limited (5/10min for guests,
   30/10min for members)
2. Validates input via Zod (`leadInsertSchema`)
3. **Critically:** ignores `assigned_to` from client body (prevents anonymous
   assignment)
4. For authenticated users: name/phone come from `users` table (server-side),
   never from body
5. Resolves agent via property ownership or `DEFAULT_AGENT_UUID` env var
6. Creates `crm_contacts` row (or reuses existing)
7. Creates `crm_leads` row
8. Creates `crm_interests` row (if property linked)
9. Logs activity to `crm_activities`
10. Sends notification via `notifyEvent()` (agent or admin fallback)

**Columns (from PostgREST OpenAPI, MANUAL verification):**
`crm_leads` has 12 columns including `assigned_to`, `created_by`, `contact_id`,
`property_id`, `status`, `budget`, `source`, `notes`.

**IMPORTANT: `CRMLead` in `types/crm.types.ts` does NOT declare `created_by`
or `user_id`**, even though RLS and application code depend on them. The actual
column set can only be confirmed against the live database.

### Pipeline

**PIPELINE DEFINITION CONFLICT — REQUIRES BUSINESS RULE VERIFICATION**

Two sources define different stage orders:

| Source | Order |
|--------|-------|
| `components/crm/CrmKanbanBoard.tsx` `STATUS_STAGES` | `new → contacted → qualified → proposal → negotiation → won/lost` |
| `types/crm.types.ts` `LeadStatus` union | `new → contacted → qualified → negotiation → proposal → won/lost` |

The Kanban board order matches the business documentation. The type union is
the outlier. `docs/crm/04-pipeline-rules.md` §0 states: "Resolve before writing
any validator."

**Current pipeline behavior:**
- **No server-side pipeline validation exists.** Stage changes are plain column
  updates from the browser.
- Kanban drag-and-drop writes directly: `.update({ status: nextStatus,
  updated_at })`
- `canDragAndMove` guard only excludes `viewer/tamu/guest`
- Agent can set any stage, any order, including `won` and `lost`
- `lost_reason` column does not exist anywhere in the repository
- No "Deal Submitted" or "Pending Verification" states exist
- No pipeline history exists (closest is a `crm_activities` row with no
  before/after values)

### Follow-up

**Statuses:** `pending`, `completed`, `cancelled` (no `OVERDUE` or
`ESCALATED`).

**Three write paths exist:**
| Operation | Path | Authorization |
|-----------|------|---------------|
| Create | `crm.service.ts` → `POST /api/leads/[id]/follow-up` | `requireRole([...])`, no Lead-ownership check |
| Read | `crm.service.ts` `getFollowups`, browser → PostgREST | none |
| Update | `crm.service.ts` `updateFollowup`, browser → PostgREST | none |
| Delete | `crm.service.ts` `deleteFollowup`, browser → PostgREST | none |

**PHASE 1A constraint met:** RLS on `crm_followups` is now enabled (migration
013). The update and delete paths that depend on the absence of RLS were
addressed simultaneously.

**IMPORTANT: `crm_followups` has no `created_by` column** (verified against
PostgREST OpenAPI). Four code sites read it — see `docs/crm/00-schema-baseline.md`
§10.

### Activities

- `crm_activities` has 6 columns: `id`, `lead_id`, `activity_type`,
  `user_id`, `notes`, `created_at`
- **No `updated_at` column** (the TypeScript type declares one — see
  `docs/crm/00-schema-baseline.md` §10)
- `activity_type` is free-form `varchar(50)` with no CHECK constraint
- Activities are **updatable by their own author** (`user_id = auth.uid()`)
- Activities are **deletable by super_admin** via `/api/admin/logs` (DELETE,
  max 500 IDs)
- The admin UI presents `crm_activities` as "System Logs" — but this is NOT an
  audit log. See §10.

### Interests

- `crm_interests` links leads to properties
- 8 columns: `id`, `lead_id`, `property_id`, `interest_level`, `notes`,
  `created_at`, `updated_at`, `status`
- No UNIQUE constraint on `(lead_id, property_id)` — duplicate interests
  can be created (M-8)
- `interest_level` has no CHECK constraint (M-7)

## 10. CRM Security Model

### VERIFIED

| Control | Evidence |
|---------|----------|
| RLS enabled on all 5 CRM tables | Migration 013, `scripts/verify-rls.mjs`, PostgREST verification |
| `anon` revoked from all CRM tables | Migration 012 (PHASE 1A), Migration 013 (PHASE 1B) |
| Ownership-based `crm_leads` SELECT | `crm_lead_visible()` function (migration 013) |
| Ownership-based `crm_contacts` SELECT | `crm_contact_visible()` function (migration 013) |
| `commissioner` read-only at DB level | `is_crm_reader()` includes commissioner but only in SELECT policy |
| `marketing` read-only at DB level | `is_crm_reader()` includes marketing but only in SELECT policy |
| `super_admin` role lock | Migration 010 — only super_admin can change role column |
| Admin audit log append-only | Migration 011 — no INSERT/UPDATE/DELETE policies |
| `is_staff()` canonicalized | Migration 016 — `'admin','super_admin'` only |

### KNOWN GAPS

| Gap | Severity | Detail |
|-----|----------|--------|
| **No server-side CRM authorization layer** | CRITICAL | `services/crm.service.ts` imports browser Supabase client. ~30 CRM functions go browser → PostgREST directly. No CRM server actions. |
| **Phone masking is client-side only** | CRITICAL | Real phone numbers are in the API payload. 8 components implement literal `"08xx-xxxx-xxxx"` replacement. See `docs/crm/02-roles-permissions.md` §6. |
| **No pipeline transition validation** | HIGH | Agent can set any stage in any order. No `lost_reason`. No Deal Submitted state. |
| **No CRM audit events** | HIGH | `admin_audit_log` has exactly 5 action types, none CRM. `AuditAction` = `user.role_change \| user.status_change \| user.delete \| logs.delete \| settings.ai_toggle` |
| **`crm_activities` is mutable by its author** | HIGH | `user_id = auth.uid()` can UPDATE their own activity rows. Not an audit log. |
| **No assignment history** | MEDIUM | Reassignment overwrites in place. No history table. |
| **Duplicate FKs on `crm_leads.assigned_to`** | MEDIUM | Both `auth.users` and `public.users` — M-6 |
| **No CHECK constraints** | MEDIUM | `status`, `interest_level`, `activity_type` have no CHECK constraints — M-7 |
| **No UNIQUE on `crm_interests(lead_id, property_id)`** | MEDIUM | Duplicate interests possible — M-8 |
| **`commissioner` role not in `UserRole` type** | MEDIUM | RLS grants read access, app demotes to viewer |

### Database Security

- **RLS policies:** All 5 CRM tables have RLS enabled with 4 policies each
  (SELECT, INSERT, UPDATE, DELETE), all bound to `authenticated` role.
  No policy uses `USING (true)`.
- **Grants:** `anon` has all CRM privileges revoked (SELECT, INSERT, UPDATE,
  DELETE, EXECUTE on helpers). `authenticated` has SELECT on all tables + row-
  specific INSERT/UPDATE/DELETE.
- **Service role:** `createAdminClient()` in `lib/supabase/admin.ts` bypasses
  all RLS. Used only in 5 lib files: `ai-quota.ts`, `audit-log.ts`,
  `fonnte.ts`, `notification-helper.ts`, and `supabase/admin.ts`.
- **Column grants:** `public.users` has column grants — anon gets only
  `(id, full_name, avatar_url)`. `guard_users_privileged_columns()` trigger
  prevents unauthorized role changes.

## 13. AI Architecture

### Provider chain

```
Agnes AI (agnes-2.0-flash) → Groq (llama-3.3-70b-versatile) → Gemini (3-model fallback)
```

Each provider failure is logged and the chain continues to the next. If all
three fail, an `Error` is thrown.

### Gemini internal fallback

```
gemini-3.5-flash-lite → gemini-2.5-flash → gemini-2.0-flash
```

Both text generation and Vision (invoice scan) use this internal 3-model
fallback. The Groq and Agnes providers are single-model with no internal
fallback.

### AI features

| Feature | Quota/day | Burst/min | Endpoint |
|---------|-----------|-----------|----------|
| `chat` | 15 | 10 | `/api/chat` |
| `generate` | 40 | 8 | `/api/ai/generate` |
| `followup` | 30 | 8 | `/api/ai/followup` |
| `scan_invoice` | 20 | 5 | `/api/ai/scan-invoice` |
| `parse_listing` | 20 | 5 | `/api/parse-listing` |
| `dashboard_summary` | 6 | 3 | `/api/dashboard/summary` |

### Quota enforcement (4 layers, in order)

1. **Super Admin bypass** (unless `dashboard_summary` — in `NO_ROLE_BYPASS`
   set)
2. **Burst per IP** (in-memory, 60s window, per-feature limits)
3. **Per-feature daily request count** (PostgreSQL atomic via
   `consume_ai_quota()` RPC)
4. **Per-user daily token budget** (60,000 default, multiplied by role
   multiplier)
5. **Global system daily token budget** (1,500,000 default)

### Role multipliers

| Role | Multiplier |
|------|-----------|
| `viewer` / `client` | 0.5x |
| `marketing` / `agent` / `commissioner` | 1x |
| `admin` | 3x |
| `super_admin` / `superadmin` | Infinity (except dashboard_summary) |

### Token estimation

- Text: `estimateTokens(input)` = Math.ceil(string length / 4)
- Images: `estimateImageTokens(bytes)` = Math.ceil(bytes / 1024)

### Known issues

- **`scan-invoice` route missing `quota.commit()`:** Token accounting is
  incomplete — only the image-based estimate is recorded, actual response
  tokens are never added.
- **`AGNES_API_KEY` optional:** If unset, the Agnes provider is called with
  `undefined`, causing a guaranteed failure before falling through to Groq.
  Adds unnecessary latency.
- **Rate limiting is in-memory only:** On multi-instance deployments, the
  effective burst limit is `limit × instance_count`. This is documented as
  intentional ("zero-cost emergency brake").
- **Fail-open on database outage:** If the PostgreSQL RPC is unavailable, all
  three database-backed quota layers are silently skipped. Only the in-memory
  burst limiter remains.

### `notifyEvent()` flow

1. Deduplicate recipients
2. Fetch user preferences from `users` table
3. Filter by event `prefKey` (only explicit `false` skips, `undefined` =
   allowed)
4. Insert bell rows to `notifications` table (via `createAdminClient`)
5. Filter push targets (`push_notifications !== false`)
6. Call `sendPushToUsers()` with filtered list
7. Push failures are logged but do not fail the main operation

### OneSignal identity lifecycle

```
Page Load:
  ensureInit() → OneSignal.init() → setStatus(null)
  getUser() → if user exists → sync(user.id) → OneSignal.login(user.id)

User Logs In:
  onAuthStateChange("SIGNED_IN") → sync(user.id) → OneSignal.login(user.id)

User Logs Out:
  onAuthStateChange("SIGNED_OUT") → sync(null) → OneSignal.logout()
```

**Key safeguards:**
- `lastSynced` prevents duplicate `login()` calls for the same user
- Only `SIGNED_OUT` triggers `sync(null)` — `INITIAL_SESSION` with null
  session does NOT unlink (prevents public pages from unlinking devices)
- `getUser()` errors do NOT trigger logout (prevents transient network errors)
- `initStatus` is `"origin"` (origin mismatch) or `"load"` (SDK load failure)
  — gates all login/logout calls
- Service worker: `public/OneSignalSDKWorker.js` (bundled SDK v16, not CDN
  importScripts — fixes spec compliance issues)
- Welcome notification: disabled

### OneSignal 409 error handling

The string `"aliases claimed"` is NOT in the `NO_RECIPIENT_MARKERS` list in
`lib/onesignal.ts`. A 409 response from OneSignal (external_id already linked
to another player) is treated as `"failed"`, not `"no_recipient"`. This is
correct behavior but there is **no recovery mechanism** for this state.

### WhatsApp (Fonnte)

- `sendWaToAgent()` in `lib/fonnte.ts` — server-side only (uses
  `createAdminClient`)
- Queries `users.phone`, `users.preferences` — checks
  `whatsapp_notifications !== false`
- Phone formatting: strips non-digits, replaces leading `0` with `62`
  (Indonesia-specific)
- Sends via `POST https://api.fonnte.com/send` (form-encoded body)
- No timeout, no retry logic
- WhatsApp is NOT triggered automatically from lead intake (confirmed:
  `app/api/leads/route.ts` lines 26-29)

## 15. Storage & Media

### Supabase Storage

- **Bucket `property-media`:** 10MB max, JPEG/PNG/WebP only (migration 008)
- **Bucket `avatars`:** 5MB max, JPEG/PNG/WebP only (migration 008)
- **Bucket `ktp`:** commented out in migration 008 (not yet created, intended
  private with signed URLs)

### Upload flow

1. `POST /api/media/upload` — authenticated, ownership-checked
2. File type check: `file.type.startsWith("image/")` — **client-declared MIME,
   no magic byte verification**
3. Size check: 10MB max
4. Ownership check: user must be `admin`/`super_admin`, or `created_by` or
   `assigned_to` of the property
5. Watermark: server-side via `sharp` — composite `public/watermark.png` at
   center, 70% opacity, 30% size, 20px margin
6. Convert to PNG, quality 85
7. Upload to Supabase Storage
8. Insert `property_media` row
9. On insert failure: cleanup uploaded file from storage

### Watermark

- `lib/watermark.ts` — `addWatermark(imageBuffer, options?)`
- Uses `sharp` for image processing (Node.js native, server-only)
- If watermark file (`public/watermark.png`) is missing, original image is
  returned unmodified

## 20. Development Rules for AI Agents

### Rule 1 — Inspect Before Modify

Read the relevant files before making changes. Understand the existing
implementation, its dependencies, and its security implications. Check
`docs/project-rules.md` and `docs/crm/` for documented constraints.

### Rule 2 — Never Guess Database Schema

The `crm_*` tables were created manually in the SQL Editor. Their schema is
**not reproducible from this repository**. If you need to know a column type,
nullability, default, or constraint:

- Check `docs/crm/00-schema-baseline.md` first
- If not there: **STOP** and mark as [UNVERIFIED] or [PRODUCTION VERIFICATION
  REQUIRED]
- Never write a migration against an assumed schema

### Rule 3 — Server-Side Security

- Client-side validation is NOT a security boundary
- `proxy.ts` is an optimistic check, NOT the sole security layer
- Every CRM operation that returns or mutates protected data must eventually
  have server-side authorization
- Phone masking must be server-side (currently client-side only)
- Do not rely on RLS alone when a server-side check is appropriate

### Rule 4 — Preserve Existing Behavior

- Do not replace working functionality without understanding it
- Do not delete or rename existing CRM columns without understanding migration
  impact
- The `crm_activities` table is mutable and serves as both business activity
  and admin "System Logs" — do not change its behavior without understanding
  both roles

### Rule 5 — Small, Reviewable Changes

- Work phase by phase. Do not implement the entire CRM upgrade in one operation
- Follow the phase order in `docs/crm/10-implementation-phases.md`
- After each phase: inspect, implement, test, verify, report
- Do not continue when a phase introduces unresolved security or data-integrity
  problems

### Rule 6 — No Destructive Database Changes

- Do not DROP, DELETE, or ALTER destructively without verification
- Do not modify existing migrations — create new ones
- Do not modify production schema manually when a migration is appropriate
- `crm_activities` has `ON DELETE CASCADE` from `auth.users` — deleting a user
  will delete their activity rows. This is documented as M-1.

### Rule 7 — Type Safety

Avoid:
- `any` (except where already present and documented)
- `@ts-ignore`
- Unsafe type casts (`as any`, `as unknown as T`)
- `!` (non-null assertion) for environment variables

Prefer:
- Strict Zod schemas for all API inputs
- Proper TypeScript types (no `| string` escape hatches)
- `validate()` helper from `lib/validations.ts`

### Rule 8 — Test Before Completion

After making changes, verify with available tools:
- `npm run lint` (ESLint)
- `npm run build` (TypeScript compilation)
- `node scripts/verify-rls.mjs` (RLS verification — but note it doesn't cover
  all tables yet)

### Rule 9 — Do Not Commit Automatically

- Do not commit, push, or deploy unless explicitly instructed
- Do not amend commits or force-push
- If a commit is needed, review the diff first

### Rule 10 — Document Uncertainty

Use these markers instead of guessing:

- **[UNVERIFIED]** — Cannot be proven from the repository
- **[PRODUCTION VERIFICATION REQUIRED]** — Requires checking the live database
- **[CONFLICTING]** — Two sources disagree
- **[INFERRED]** — Strong conclusion from code structure, but not directly
  verified

Never change an INFERRED to VERIFIED without evidence.

### Rule 11 — Do Not Modify Migration Files

- Existing migrations (001–014) are committed and applied. Do not modify them.
- Untracked migrations (015–017) are PHASE 2 preparation. Do not apply them
  without instruction.
- New migrations should be created as new files with sequential numbering.

### Rule 12 — Do Not Assume Documentation is Correct

- `docs/crm/` contains CURRENT STATE (verified) and TARGET STATE (not
  implemented). Always check which is which.
- `docs/crm/10-implementation-phases.md` has known documentation drift — it
  lists PHASE 1A/1B as "pending" but they are CLOSED.
- If documentation contradicts source code, record the conflict. Do not resolve
  by assumption.

### Rule 13 — Language Convention

- Code comments and internal documentation are in Bahasa Indonesia
- `docs/crm/` and `docs/project-rules.md` are in English
- Keep each document in the language it already uses
- Follow the existing repository convention for new code
