## 1. Purpose

**TARGET STATE.**

PLM CRM manages property Leads generated by the PLM website.

The main business objective is to make every company Lead:

-   traceable
-   assigned
-   followed up
-   auditable
-   protected from unauthorized access
-   reviewable through its lifecycle

The CRM must reduce the opportunity for Lead leakage or off-system
transactions while remaining fair to Agents.

**CURRENT STATE note.** The audit found that the two controls most
directly aimed at Lead leakage --- phone masking and Lead visibility ---
are not enforced. Every Agent can read every Lead, and real customer
phone numbers reach the browser. See
`docs/crm/02-roles-permissions.md` §6 and
`docs/crm/03-lead-governance.md` §4.

## 2. Company Lead

**CURRENT STATE --- verified.** A Lead generated through the PLM website
is a company Lead. The flow below is implemented in
`app/api/leads/route.ts` (POST, intentionally public, service-role
client, rate limited: GUEST 5 / MEMBER 30 per 10 minutes):

Property/Dashboard → WhatsApp CTA → Lead form → name/full name →
WhatsApp number → optional message/note → Lead creation → CRM Lead →
activity row

The route writes `crm_contacts` (`contact_code: CONT-${Date.now()}`),
`crm_leads`, `crm_interests` (priority 1, interest level `high`) and
`crm_activities`. It reuses an existing open Lead rather than creating a
duplicate.

Two protections already exist and should be preserved:

-   a body-supplied `assigned_to` is **ignored**
-   `status` is **forced** to `new`

The original source must be preserved.

Recommended conceptual source:

`WEBSITE`

Recommended source detail:

`PROPERTY_WHATSAPP_FORM`

Use existing fields if equivalent fields already exist. Whether such
fields exist cannot be confirmed from the repository --- see
`docs/project-rules.md` §15.

## 3. Lead Is a Company Asset

**TARGET STATE.**

An Agent is responsible for a Lead but does not personally own the Lead.

The company retains the Lead relationship and history.

This principle must be reflected in:

-   ownership
-   permissions
-   pipeline
-   Follow-Ups
-   audit
-   reassignment
-   closing verification

**CURRENT STATE --- partially contradicted.** `crm_leads_delete` in
`007_rls_properties_users_billing.sql` reads:

    public.is_staff() or created_by = auth.uid()

so an Agent can hard-delete a Lead they created. There is also no
assignment history, so a reassignment overwrites the previous owner with
no trace.

## 4. Existing Roles

**CURRENT STATE --- corrected.** The previous revision listed four roles.
The database and the type system between them recognise more:

| Role | In `UserRole` type | In `is_internal_staff()` RLS | CRM permission |
| --- | --- | --- | --- |
| `super_admin` (legacy spelling `superadmin`) | yes | yes | all |
| `admin` | yes | yes | `manage_all_crm` |
| `agent` | yes | yes | `manage_own_crm` |
| `marketing` | yes | **no** | `manage_own_crm` |
| `viewer` | yes | no | `view_own_crm` |
| `commissioner` | **no** | **yes** | none defined |

Two mismatches to resolve, not to ignore:

-   `commissioner` has read access to every `crm_lead`, `crm_contact`
    and `crm_activity` through `is_internal_staff()` but has no
    representation in the application layer at all. It must be either
    removed from the RLS helpers or defined properly. Decision is due in
    PHASE 1B.
-   `manage_own_crm` is **never enforced at row level**. RLS uses
    `is_internal_staff()`, which does not distinguish "own" from "all".
    The permission that separates Agent from Admin in TypeScript has no
    effect in the database.

Viewer/Guest does not have CRM access. Verified: `canAccessRoute` in
`lib/permissions.ts` default-denies and requires one of
`manage_own_crm`, `manage_all_crm`, `view_all_crm`, `view_own_crm`.

## 5. Existing Pipeline

**TARGET STATE.** Preserve the existing business stages:

1.  New Lead
2.  Contacted
3.  Qualified
4.  Proposal
5.  Negotiation
6.  Won (Deal)
7.  Lose

**CURRENT STATE --- there is an order conflict inside the codebase.**

| Source | Order |
| --- | --- |
| `components/crm/CrmKanbanBoard.tsx` `STATUS_STAGES` | new, contacted, qualified, **proposal, negotiation**, won, lost |
| `types/crm.types.ts` `LeadStatus` union | ... **negotiation, proposal** ... |

The Kanban board agrees with this document; the type union does not. One
of them must be made authoritative **before** any transition validator is
written, otherwise legitimate Leads will appear to have made invalid
jumps.

Do not rename database values without inspecting existing records. The
repository does not contain the `crm_leads` DDL, so it is unknown whether
`status` carries a CHECK constraint or is free text --- see
`docs/project-rules.md` §15. Inspect the live distribution of `status`
values before touching them.

## 6. Active Lead

**CURRENT STATE --- implemented.** An active Lead is any Lead that has
not reached a terminal state. `app/api/leads/route.ts` uses
`.not("status","in","(won,lost)")` when deciding whether to reuse an
existing Lead.

Terminal states are normally:

-   Won
-   Lose

**TARGET STATE.** Active Leads should have a clear responsible Agent when
assigned.

## 7. Follow-Up

A Follow-Up represents a planned business action.

Examples:

-   call customer
-   WhatsApp customer
-   send property information
-   arrange viewing
-   confirm budget
-   confirm purchase intention

**TARGET STATE.** The CRM should encourage an active Lead to have a next
action. Not implemented; see `docs/crm/05-follow-up-rules.md` §10.

## 8. Lost

**TARGET STATE --- not implemented.**

An Agent must not mark an active Lead as Lost without a reason.

The reason must be stored as structured data where practical, with
optional explanation.

**CURRENT STATE.** `lost_reason` does not exist anywhere in the
repository --- no column reference, no type, no UI. An Agent can set
`status = "lost"` with no reason and no server-side check, because
`services/crm.service.ts` `updateStatus` performs a bare update from the
browser. Delivery is PHASE 3.

## 9. Won

**TARGET STATE --- not implemented.**

An Agent may submit a deal, but final verification should belong to
Admin or Super Admin.

This separates sales activity from company verification.

**CURRENT STATE.** There is no Deal Submitted state, no Pending
Verification state, and no verification step. An Agent can write
`status = "won"` directly, from the Kanban board
(`components/crm/CrmKanbanBoard.tsx` performs
`.update({ status: nextStatus, updated_at })`) or through
`crm.service.ts`. Delivery is PHASE 3.

## 10. Auditability

**TARGET STATE --- not implemented.**

Important business events must be recorded in the existing Admin →
System Logs infrastructure.

**CURRENT STATE.** Two distinct systems exist and neither currently
records CRM audit events:

-   `admin_audit_log` --- immutable by design, but its `AuditAction`
    type has exactly five values, none of them CRM
-   `crm_activities` --- what the "Admin → System Logs" UI actually
    reads and deletes; mutable by its own author, therefore not an audit
    log

See `docs/crm/06-audit-system.md` for the full comparison and the chosen
target. Delivery is PHASE 2.

## 11. Fairness

**TARGET STATE.**

Risk detection must identify patterns for review.

The CRM must not automatically label an Agent as dishonest, fraudulent,
or guilty.

Not implemented; the Risk Engine is PHASE 6.

## 12. AI

**TARGET STATE.**

AI is an assistant.

AI recommendations do not override:

-   permissions
-   ownership
-   pipeline rules
-   audit rules
-   closing verification
-   administrative decisions

**CURRENT STATE.** No CRM AI exists. The underlying AI infrastructure
does exist and is reusable. CRM AI is PHASE 7 and must not be
implemented before authorization, ownership, RLS, audit and risk
foundations are complete. AI must never become part of the authorization
path.
