# PLM CRM --- Pipeline Governance

> **Document status:** revised in PHASE 0.5 --- Documentation Reconciliation,
> 2026-08-08.
>
> **CURRENT STATE** = verified by the PHASE 0 audit.
> **TARGET STATE** = intended design, not implemented unless stated.
>
> A TARGET STATE rule is never evidence that a control exists.

## 0. CURRENT STATE --- Pipeline Governance Added in PHASE 3

Phase 3 adds a single server-side transition path, structured Lost reasons,
Deal submission/review state, and authoritative audit events. The additive
migration must be applied before deploying these paths.

The earlier audit findings below remain historical context:

**There is no pipeline endpoint.** A stage change is a plain column
update sent from the browser. `services/crm.service.ts`:

    async updateStatus(id, status) {
      // bare update
      await this.logActivity({
        activity_type: "status_change",
        notes: `Status berubah menjadi ${status}`,
      });
    }

No transition validation, no previous value recorded, no actor/role
recorded, no reason. Kanban drag-and-drop writes directly:
`components/crm/CrmKanbanBoard.tsx` performs
`.update({ status: nextStatus, updated_at })`, and its `canDragAndMove`
guard only excludes viewer/tamu/guest.

Consequences:

-   an Agent can set any stage, in any order, including `won` and `lost`
-   §12 of this document ("backend must reject invalid transitions") has
    no backend to do the rejecting
-   `lost_reason` does not exist anywhere in the repository
-   no Deal Submitted or Pending Verification state exists
-   no pipeline history exists; the closest artefact is a
    `crm_activities` row of type `status_change` with no before/after
    values

**Stage order conflict.**

| Source | Order |
| --- | --- |
| `components/crm/CrmKanbanBoard.tsx` `STATUS_STAGES` | new, contacted, qualified, **proposal, negotiation**, won, lost |
| `types/crm.types.ts` `LeadStatus` union | ... **negotiation, proposal** ... |

The Kanban board matches §1 below; the type union does not. Resolve
before writing any validator.

**Schema unknown.** The `crm_leads` DDL is not in the repository, so it
is unknown whether `status` has a CHECK constraint, an enum type, or is
free text. Adding new values may be trivial or may collide with an
invisible constraint. Verify against the live database in PHASE 0.75
before designing §9.

## 1. Existing Pipeline

**CURRENT STATE --- values in use, order per the Kanban board.**

`New Lead → Contacted → Qualified → Proposal → Negotiation → Won`

with:

`Lose`

as the terminal loss state.

Preserve existing database compatibility. Inspect the live distribution
of `status` values before changing anything.

## 2. Pipeline History

**TARGET STATE --- not implemented.**

Every pipeline transition should record:

-   Lead
-   previous stage
-   new stage
-   actor
-   role
-   timestamp
-   reason where required

Use the existing System Logs architecture.

**CURRENT STATE.** A `crm_activities` row is written with
`activity_type: "status_change"` and a free-text note. It carries neither
the previous stage nor the actor's role, and the note is generated
client-side. `crm_activities` is also updatable by its own author, so it
cannot serve as pipeline history.

Target store is `admin_audit_log`, not `crm_activities` --- see
`docs/crm/06-audit-system.md`. Delivery is PHASE 2.

## 3. New Lead → Contacted

**TARGET STATE.**

The Agent should perform or record a meaningful contact activity where
the current CRM supports it.

Do not silently change the stage without an audit event.

**CURRENT STATE.** The stage changes silently. An activity row is
written, but it is generated by the client and is not an audit event.

## 4. Contacted → Qualified

**TARGET STATE.**

Qualification should preserve relevant Lead information such as:

-   budget
-   property interest
-   customer intent
-   notes

Use existing fields where possible.

**CURRENT STATE.** Property interest is stored in `crm_interests` --- a
table with **no RLS**, so it is exposed to the anon key. Whether budget
and intent fields exist cannot be confirmed from the repository. No
qualification gate exists; the stage can be set without any of this
information.

## 5. Qualified → Proposal

**TARGET STATE.**

Proposal stage should retain the property/proposal context associated
with the Lead.

**CURRENT STATE.** Not enforced. Context lives in `crm_interests`, which
is unprotected.

## 6. Proposal → Negotiation

**TARGET STATE.**

Record the transition and preserve related activity.

**CURRENT STATE.** Not recorded as audit. See §2.

## 7. Lose

**TARGET STATE --- not implemented.**

An Agent cannot mark a Lead as Lose without a structured reason.

Suggested reasons:

-   customer not responding
-   budget mismatch
-   not interested
-   chose another property
-   purchase postponed
-   property unsuitable
-   duplicate
-   other

If `Other` is selected, require an explanation.

**HISTORICAL AUDIT FINDING.** `lost_reason` did not exist --- no column reference,
no type, no UI, nowhere in the repository. An Agent can set
`status = "lost"` from the Kanban board with no reason and nothing to
stop them. This is one of the two prerequisites for the Risk Engine
signal "Lost without sufficient activity"
(`docs/crm/07-risk-engine.md` §4). Delivery is PHASE 3.

## 8. Lose Does Not Mean Delete

**TARGET STATE.**

A Lost Lead remains part of company history.

Do not delete:

-   customer history
-   original source
-   ownership history
-   activity history
-   Follow-Up history

**CURRENT STATE --- contradicted in two places.**

-   `crm_leads_delete` is `is_staff() or created_by = auth.uid()`, so an
    Agent can hard-delete a Lead they created.
-   `crm_activities` rows are deletable by `super_admin` through
    `app/api/admin/logs/route.ts` (max 500 ids per call), which is the
    "System Logs" delete function. Activity history is therefore
    intentionally destructible.

Ownership history and Follow-Up history are not protected because neither
exists as history.

## 9. Won

**TARGET STATE --- not implemented.**

Recommended workflow:

`Negotiation` → `Deal Submitted` → `Pending Verification` →
`Admin/Super Admin Review` → `Won`

If the current schema cannot represent a pending state, implement the
closest compatible mechanism without corrupting existing pipeline
values.

**PHASE 3 IMPLEMENTATION.** Deal state is stored separately from the live
Lead status vocabulary. Agents submit from `negotiation`; Admin/Super Admin
approve or reject. Only a verified Deal may reach `won`. Existing `won` rows
remain unchanged.

**PHASE 0.75 dependency.** Whether the intermediate states can be added
as `status` values depends on constraints that are not visible in the
repository. Inspect the live schema first; if `status` is constrained,
decide between extending the constraint and adding a separate
verification column, and record the decision here.

## 10. Self-Verification

**TARGET STATE --- not implemented.**

Agent must not be the final verifier of their own Deal.

**CURRENT STATE.** There is no verification step at all, so there is
nothing separating submission from verification. Delivery is PHASE 3,
audited under PHASE 2 (`DEAL_SUBMITTED`, `DEAL_VERIFIED`,
`DEAL_REJECTED`).

## 11. Administrative Override

**TARGET STATE --- not implemented.**

Admin/Super Admin may override permitted pipeline states.

Override must record:

-   actor
-   previous state
-   new state
-   reason
-   timestamp

**CURRENT STATE.** Admin writes are indistinguishable from Agent writes
because nothing is recorded. An override is currently just an update.

## 12. Direct API Manipulation

**TARGET STATE.**

Frontend restrictions are insufficient.

Backend must reject invalid transitions even when an Agent manually
calls the endpoint.

**CURRENT STATE --- stronger than the original wording implies.** There is
no CRM endpoint to call. Stage changes go browser → PostgREST as a column
update, so the only thing that could reject an invalid transition is a
database-level constraint, trigger, or policy --- and none exists for
transitions.

Testing must therefore include direct PostgREST calls with the anon key,
not only "direct API access".

Delivery is PHASE 3, and it depends on PHASE 1B introducing a
server-side write path.

## 13. Legacy Data

**TARGET STATE.**

Existing Leads with invalid historical transitions must not be silently
rewritten.

Treat them as historical data.

**CURRENT STATE note.** Because no transition has ever been validated,
assume the live data contains sequences that a new validator would call
invalid. Inspect the actual distribution of `status` values in PHASE 0.75
and design the validator to accept existing rows as given, applying
validation to new transitions only.
